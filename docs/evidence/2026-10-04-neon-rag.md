## Outcome and scope

The existing Neon project passed actual pgvector retrieval and unchanged migration
verification on an isolated production-shaped branch and a fresh database.
PostgreSQL reported **18.6**, pgvector **0.8.6**, and pg_trgm **1.6**. A Windows
pgvector installation was unnecessary for this hosted target.

This is database/software evidence using hand-authored vectors and synthetic text.
It is not Arabic semantic recall, an embedding-model benchmark, corpus ingestion,
source-edition approval, scholarly assessment, or production deployment evidence.
The reusable smoke script is read-only; the branch integration fixtures and
temporary role membership changes were rolled back.

## Retrieval and authorization checks

Both isolated databases passed:

- Exact cosine ranking with `<=>`, ordered by ascending distance and a deterministic
  ID tie-break. Synthetic distances were `0`, approximately `0.200000036`, and `1`.
- A separate pg_trgm lexical query selected the literal-match fixture with similarity
  `1`; the manually nearest vector fixture had different wording. This demonstrates
  separate ranking paths, not the quality of either path on Arabic sources.
- The read-only fixture query excluded pending/revoked approval states and mismatched
  model ID, document task type, corpus version, and dimensions before distance evaluation.
  Unknown model space returned no candidates.
- Query validation rejected dimension mismatch, non-finite values, zero cosine vectors,
  and an incompatible query task. Postgres rejected comparison/cast dimension mismatch
  with SQLSTATE `22000`.
- Actual `basirah.source_edition`, `passage`, and `passage_embedding` RLS exposed only
  the synthetic approved edition to `basirah_runtime`. Pending, rejected, and revoked
  editions stayed hidden. The actual embedding dimension constraint rejected a
  two-dimensional vector declared as three-dimensional with SQLSTATE `23514`.
- Runtime embedding writes, private signing-state reads, and worker-function calls
  were denied. Worker direct document-table and private signing-state reads were denied.
- Guest sessions could not read another session's document or report. Revision updates
  failed with SQLSTATE `55000`.
- A worker acquired a bounded lease, rejected a forged heartbeat token, accepted the
  valid token, persisted an allowed failure, and rejected subsequent heartbeats.
- A second run bound its evidence-state hash, rejected a completion with changed input
  hash, persisted an empty-evidence `needs_review` report, rejected completion replay,
  and exposed that report only to its owning guest session.

The empty-evidence completion tests conservative persistence and ownership only.
The experiment did not validate real citations, nonempty reports, cancellation races,
expired/reclaimed leases, production login delivery, or every migration verifier check.
Those remain separate acceptance coverage.

## Reproduce the read-only vector smoke

[verify-vector-retrieval.mjs](../../scripts/verify-vector-retrieval.mjs) uses the existing
`pg` dependency and installs no extensions, adds no tables, and changes no corpus rows.
It requires a direct TLS-verified connection supplied securely as
`RAG_DATABASE_URL_UNPOOLED` in the invoking process environment:

```bash
node scripts/verify-vector-retrieval.mjs
```

No connection value belongs in shell history, a report, or source control. A successful
JSON receipt contains version metadata, synthetic ranking results, and guard outcomes
only. Driver errors are reduced to a safe error code.

Local experimental receipts remain under the same workspace's
`Project_Code/AI_Foundation/experiments/rag-next-v1`: `INITIAL_REPORT.json` records
the actual first migration application; `REPORT.json` records extended checks;
`CLEANUP.json` records the read-only production recheck and confirmed branch deletion.
They contain metadata and synthetic outcomes, not credentials or source text.
The experimental branch IDs have been deleted; rerunning branch provisioning requires
a newly verified isolated target, not production.

Skills used: workspace `neon` and `neon-postgres`. Query operator behavior was checked
against the [official pgvector repository](https://github.com/pgvector/pgvector).
The [Neon documentation index](https://neon.com/docs/llms.txt) identifies the current
branching and CLI references. Subsequent integration must retain approved-edition
filtering, compatible query/document embedding configuration, original-text attribution,
and explicit degraded lexical/reference retrieval while no real embeddings exist.
